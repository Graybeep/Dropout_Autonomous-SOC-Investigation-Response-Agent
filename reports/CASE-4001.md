### Sufficiency assessments

> **Alert facts:** SQL injection attempt (UNION SELECT signature) from 198.51.100.88 to 10.20.4.77:3306 against asset SRV-FIN-07. Port 3306 is MySQL. Sensor says "critical" — which is an opinion, not evidence.

**Hypothesis to test:** For this attack to have *succeeded*, all of the following must hold:
1. SRV-FIN-07 must be running a MySQL version inside an affected range for the relevant SQLi-class CVE (i.e., not already patched).
2. The host-side logs must show the injected query actually executing (rows returned, data read, or something spawned) — not a syntax error / 403 / zero rows.
3. The flow direction/volume must be consistent with data being extracted, not just an error response.

**What would falsify "succeeded":** a MySQL version above the fix threshold *and* logs showing the attempt erroring out or being rejected *and* a small/one-directional flow. If any of those fail to appear, I need to keep digging.

Let me gather the two independent facts I need to join: what the host runs, and what the CVEs affect.

> This is the decisive join. Let me do it explicitly:

- **SRV-FIN-07 runs MySQL 5.7.19** (Ubuntu 20.04.6 LTS, finance reporting DB, criticality critical).
- **CVE-2023-21980** (cvss 9.8, attack_class **sql_injection**) affects `>=5.7.0,<5.7.30`, fixed in 5.7.30. **5.7.19 is >= 5.7.0 and < 5.7.30 → this host IS inside the affected range.** The CVE description matches the observed attack exactly: crafted UNION payloads, unauthenticated remote read of arbitrary tables.

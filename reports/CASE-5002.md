### Sufficiency assessments

> The signature is a SQL injection attempt using UNION SELECT, but the destination port is 3306 — MySQL's port. So an external-ish host (192.0.2.66) is talking directly to a MySQL port on SRV-WEB-04. Let me establish the two independent facts I need: what version is running, and what the CVE DB says is affected.

**Hypothesis:** For this attack to have SUCCEEDED, all of the following must be true: (1) SRV-WEB-04 actually runs a MySQL version inside an affected range for a UNION-SELECT SQL injection class vulnerability, (2) host logs show a malicious query actually executing and returning data (not erroring/being blocked), and (3) packet metadata shows meaningful data flowing outward. Falsifiers: version outside all affected ranges (patched), or logs showing the query rejected/zero rows, or a tiny/benign flow with no exfil.

> **Version comparison, stated explicitly:**

- SRV-WEB-04 runs MySQL **5.7.25**.
- CVE-2023-21980 affects `>=5.7.0,<5.7.30`, fixed in 5.7.30. **5.7.25 is inside that range** (5.7.25 ≥ 5.7.0 and 5.7.25 < 5.7.30). This is a 9.8 CVSS SQL-injection-class vulnerability in the parser, matching the alert signature exactly.
- CVE-2022-21444 affects `>=8.0.0,<8.0.30`. 5.7.25 is **not** in the 8.0.x range, so that entry does not apply (and it's DoS-only, no data disclosure, irrelevant here).

So the host **IS vulnerable** to the UNION-SELECT SQL injection class. That satisfies condition (1) of my hypothesis. Now I need to know whether anything actually happened on the host and whether data left.

> This is decisive and the two independent sources agree precisely.

**What the logs show:**
1. `07:14:02` — the injected query executed: `SELECT id,title FROM articles WHERE id=3 UNION SELECT user,authentication_string FROM mysql.user--`, flagged `injected: true`. This is a real UNION SELECT reading MySQL credential hashes — not an error, not blocked.
2. `07:14:31` — a second injected query returned **Rows_sent: 38402** from `portal_users` (email, password_hash, address) over 26.7s.
3. `07:15:09` — connection from 192.0.2.66 closed after 28.9s, **1,743,908 bytes sent**.

**What the packets show:** bytes_to_client = 1,743,908 vs bytes_to_server = 2,402 — a ~726:1 outbound-to-inbound ratio, duration 28.94s (matches the log's 28.9s exactly), `exfil_indicators: true`, entropy 7.6, and anomaly `mysql_response_size_outlier`.

So conditions (1), (2), and (3) of my hypothesis are all satisfied. Now the disconfirming check: before I conclude success, I must look for any sign this was blocked/errored after the fact — e.g. a firewall block, or a history on this asset that reframes it. And I should check whether the asset has related alerts (the notes mention "the same source enumerated this asset earlier" and a `credential_reuse_same_src` anomaly).

> Both disconfirming checks are in, and both point the same way:

- **Firewall:** 192.0.2.66 is **not blocked** (no record, total_blocked 0). Nothing contained this traffic — so the "it was stopped" alternative is falsified. The 1.7 MB left the host uncontested.

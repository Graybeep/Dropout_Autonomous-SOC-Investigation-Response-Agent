### Sufficiency assessments

> Alert: SQL injection attempt (UNION SELECT) from 192.0.2.66 to SRV-WEB-04 on port 3306 (MySQL), labeled "high".

**Hypothesis (what must be true for success):** SRV-WEB-04 runs a MySQL version inside a UNION-SQLi-relevant CVE's affected range, the injected query actually executed and returned rows (visible in host logs), and/or data left the host (exfil indicators in packet metadata).

**Confirming evidence:** running MySQL version inside an affected range + logs showing an executed malicious query/rows returned + outbound payload anomaly.
**Falsifying evidence:** running version outside all affected ranges; logs showing the query errored/blocked/zero rows; benign flow with tiny response.

Let me gather the asset facts and any vuln entries in parallel.

> Critical join: SRV-WEB-04 runs **MySQL 5.7.25**. CVE-2023-21980 affects **>=5.7.0,<5.7.30** (sql_injection, CVSS 9.8). 5.7.25 < 5.7.30 → **this host IS inside the affected range**. CVE-2022-21444 affects 8.0.x only → not applicable.

So the vulnerability precondition is satisfied. Now I must check whether the attack *did* anything on the host — that's the decisive step. I need host logs and flow metadata.

> This is all consistent with a successful breach, across independent sources:

- **Host logs:** the UNION SELECT against `mysql.user` (auth bypass / credential read) executed at 07:14:02, then a second injected query `SELECT email,password_hash,address FROM portal_users` returned **Rows_sent: 38402**. That is real data returned, not an error.
- **Packet metadata:** 1,743,908 bytes sent to the attacker (matching the log's "1743908 bytes sent"), high entropy 7.6, `exfil_indicators: true`.

Now the mandatory disconfirming check: if this succeeded, I must look for any sign it was blocked or errored — and establish whether the asset has a corroborating history that changes the reading. Let me pull related alerts.

> The related alert **corroborates**: ALERT-5001 at 05:02:45 is the same source IP (192.0.2.66) against the same asset and port — the earlier *failed* enumeration that preceded this successful injection ~2 hours later. The packet metadata's `credential_reuse_same_src` note ties the same actor here. Case 5001 correctly found the *earlier* attempt failed; that does not contradict — it establishes the reconnaissance stage of this same intrusion.

**Disconfirming check performed:** I looked for signs of blocking/failure. The only error/status log entry (`mysql/error`) is not a failure — it records the connection *closing after 28.9s with 1743908 bytes sent*, which is mirrored exactly by `bytes_to_client: 1743908` in the flow metadata. There is no "Access denied", no refused/reset connection, no zero-row result. The 38,402 rows sent falsifies the "failed attempt" reading.

I have enough to classify.

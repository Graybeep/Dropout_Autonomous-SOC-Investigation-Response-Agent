### Sufficiency assessments

> Alert facts: SQL injection attempt targeting `SRV-WEB-04` on port **3306** (MySQL). Sensor labels it "high" — but that's an opinion.

**Hypothesis:** For this to have SUCCEEDED, all of these must hold:
1. SRV-WEB-04 must be running a MySQL version inside an affected range for a SQLi-relevant CVE (or the app must be genuinely injectable).
2. Host logs must show the injected query actually executing / returning rows, not erroring out.
3. Packet metadata should show data flowing back to the attacker (192.0.2.66).

**Falsifiers:** a running version above all affected ranges (patched), log entries showing a rejected/failed query, or a tiny/one-way flow with no data returned.

Let me gather the version and host facts first — these are independent sources.

> Now the version join, explicitly:

- SRV-WEB-04 runs **MySQL 5.7.25**.
- CVE-2023-21980 affects `>=5.7.0,<5.7.30`, fixed in 5.7.30. **5.7.25 is inside that range** — it is BELOW the 5.7.30 fix. Attack class is `sql_injection`, CVSS 9.8, and the description matches the alert signature exactly (crafted UNION payloads, arbitrary table read).
- CVE-2022-21444 affects `>=8.0.0,<8.0.30` — 5.7.25 is outside that range (not 8.0.x), and it's a DoS class anyway, irrelevant here.

So `version_in_range` is established for CVE-2023-21980. But **vulnerability ≠ exploitation**. Last patch date 2025-03-19, yet still running 5.7.25 — the host is unpatched for this.

Now I must check whether anything actually happened on the host, and whether data left.

> Both sources corroborate a successful compromise, and they agree on the numbers:

### Sufficiency assessments

> Alert facts: a SQL injection attempt (UNION SELECT) from 203.0.113.45 against SRV-WEB-01 on port 443, labeled "critical" by the sensor. The label is the sensor's opinion — I need to test it.

**Hypothesis:** For this attack to have SUCCEEDED, three things must hold:
1. The web service on SRV-WEB-01 must be running a version vulnerable to the relevant flaw (or the injection must reach a database that executes it).
2. Host-side activity must show the injected query actually *did something* — executed, returned rows, or otherwise changed state. An error page / 403 / zero rows means failure.
3. Data must have actually left the network (exfil indicators) if this was a data-theft injection.

**Falsifiers:** a running version outside all affected ranges (patched), clean/failed host logs, or a benign, small, error-shaped packet flow.

Let me gather the independent sources. I'll start with the asset inventory and the packet metadata in parallel, since neither depends on the other.

> Two important facts so far:

- **Asset:** SRV-WEB-01 runs Apache 2.4.58, MySQL 8.0.36, OpenSSH 8.9p1, on Ubuntu 22.04.4, last patched 2026-08-30 (12 days before the alert). OS is "high" criticality and public-facing.
- **Packets:** 412 bytes out, 1840 bytes back, 96 ms, TLS, **no exfil_indicators**, entropy 4.1, and the notes say the response is consistent with a **403 error page**. That is a strong early sign the attempt was *blocked/failed*, not successful extraction.

Now I need to test the vulnerability side. The web front end is Apache, but the injection targets a SQL backend (MySQL is co-resident here). Let me pull both CVE sets so I can do the version join explicitly, and also check host logs for what the app actually did.

> Now I can do the version join explicitly.

**MySQL (injection backend):** running **8.0.36**

The 02:15:40 entry is an aborted connection (client closed), and the 02:18:02 entry is a routine `deploy` publickey SSH login from an internal host 10.20.0.9 — not attacker-related.

So the attempt is *visible* in the logs but **demonstrably failed** — blocked, 403, no injected query executed.

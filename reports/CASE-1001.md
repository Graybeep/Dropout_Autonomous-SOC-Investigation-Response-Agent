### Sufficiency assessments

> The alert is a SQL injection attempt against SRV-WEB-01 on port 443. Severity label is "critical" but that's the sensor's opinion.

**Hypothesis for SUCCESS:** The web server on SRV-WEB-01 runs an application whose backend DB is vulnerable to UNION SELECT injection via the `443` service; the injected query actually executed and returned data; and/or that data left the host.

**Would confirm:** version of the exposed service inside an affected CVE range, host logs showing a query that executed / rows returned, or packet metadata showing anomalous outbound payload.

**Would falsify:** service version outside all affected ranges, WAF/error responses (403/400), zero-row results, or benign packet flow.

First I need to know what SRV-WEB-01 actually runs, and separately what CVEs affect that service.

> Key facts so far:

- **Host runs:** apache 2.4.58, mysql 8.0.36, openssh 8.9p1, patched 2026-08-30.
- **Flow:** 412 bytes in, 1840 bytes out, 96 ms, single request/response pair. `exfil_indicators: false`, entropy 4.1 (low). The notes say the response size is consistent with a **403 error page** and there is no sustained outbound transfer, no encoded blob.

That already points strongly toward a failed/blocked attempt. Now I need to independently verify (a) whether the running versions are actually vulnerable to any relevant CVE, and (b) whether host logs show anything executed.

> Now I can do the version comparison explicitly.

**MySQL 8.0.36 vs the CVE list:**
- CVE-2023-21980 affects `>=5.7.0,<5.7.30` — this is the **5.7.x** branch. 8.0.36 is not in the 5.7.x line at all, and it's above the 5.7.30 fix. **NOT affected.**
- CVE-2022-21444 affects `>=8.0.0,<8.0.30`. 8.0.36 **> 8.0.30**, i.e. above the fix, so **outside the affected range**. (Also it's a DoS, not data disclosure, so it wouldn't match a UNION SELECT exfil anyway.)

So the running MySQL is **outside both affected ranges** — the SQL-injection CVE does not apply to this host.

**Apache 2.4.58 vs CVE-2021-41773:** affects `>=2.4.49,<=2.4.50`; 2.4.58 is **above** the 2.4.51 fix. **NOT affected** (and it's path traversal, unrelated to this signature).

**Host logs — decisive:** At 02:14:07 the request `GET /catalog?id=17 UNION SELECT 1,2,3--` was **blocked by modsecurity** (WAF rule 942100) and Apache returned **403 with 199 bytes**. The second injection at 02:14:22 also returned **403**. The only MySQL query near that time is the *benign* pre-existing application query `SELECT name,price FROM catalog WHERE id=17` — no attacker-controlled SQL. The "Aborted connection" note is just the client closing; no data returned.

So: the attack was attempted, visible, and demonstrably **failed** — blocked at the WAF.

Now the disconfirming check. My leading hypothesis is "failed/blocked." The falsifying search is: *is there any post-exploitation activity I haven't looked at?* Specifically, did the attacker get in by another route around the WAF, and does this asset have a history that changes the reading?

> The wider window shows nothing new: no post-exploitation processes, no account creation, no attacker SQL in MySQL, just a legitimate cron job and a legitimate publickey SSH login from an internal host (10.20.0.9) — the `deploy` user's key, an internal management source, not the attacker IP 203.0.113.45. `get_related_alerts` returned **no_data** — no other alerts on this asset, so there's nothing to corroborate, and I must not cite that empty lookup as a factor.

**Disconfirming check result:** I explicitly looked for signs the attack *did* succeed despite the 403 — attacker-controlled SQL reaching MySQL, outbound data, follow-on process spawns or a new session from the attacker IP. I found none. The only MySQL query is the benign application query, the flow is a single 403 request/response pair, and `exfil_indicators` is false.

**Conclusion:** This is a failed attack. The version analysis and the host logs both independently rule out success, and the WAF log states the request was BLOCKED. The "critical" label is the sensor's opinion about the signature, not evidence the injection worked.

> Fair catch — SRV-WEB-01 also runs openssh 8.9p1, and I claimed the host is outside ALL affected ranges without checking it.

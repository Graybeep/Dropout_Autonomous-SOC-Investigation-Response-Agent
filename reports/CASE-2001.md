> Facts so far: an SQL-injection signature ("UNION SELECT") against the MySQL port (3306) of SRV-DB-02, from external IP 198.51.100.23, timestamped 2026-09-11T03:41:52Z. Sensor labels it critical.

**Hypothesis (leading):** The attacker exploited SQL injection against the database service on SRV-DB-02 and possibly extracted data.

For that to be TRUE, I'd need:
1. The running MySQL version to be inside a CVE's affected range (an injectable/exploitable state).
2. Host logs showing a malicious query actually executed / rows returned.
3. Packet metadata showing data actually left the host.

Confirmation: version in range + logs showing executed injected query + outbound payload anomaly.
Falsification: version patched outside all ranges, OR logs showing the request errored/rejected, OR packet flow showing a tiny error response with no data egress.

Let me establish vulnerability and host reality in parallel: the running version, the CVE ranges for mysql, and the flow metadata.

> Two of three checks land hard against the host:

- **Version:** SRV-DB-02 runs **mysql 5.7.21**. CVE-2023-21980 affects `>=5.7.0,<5.7.30`. 5.7.21 is **inside** that range (5.7.21 < 5.7.30). - **Packets:** 2,210 bytes out, **2,517,483 bytes back** to the external host over 41s, exfil_indicators=true, entropy 7.8, flagged `mysql_response_size_outlier` and `sustained_egress_off_hours`, ~1400× the 30-day median. That is the shape of a bulk record export, not an error page.

So version-in-range and exfil-indicators both point to success. I still need host-side confirmation (did a query actually execute?) and the asset's history.

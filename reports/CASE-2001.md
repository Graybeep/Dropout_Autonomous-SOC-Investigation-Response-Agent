### Sufficiency assessments

> **Hypothesis forming.** This is a SQL-injection signature pointed at TCP/3306 — MySQL directly on SRV-DB-02. For this attack to have SUCCEEDED, all of the following must hold:

1. **The host must actually be running a MySQL version inside an affected range** of some CVE matching a UNION SELECT SQLi attack class (a patched service would reject or be inapplicable).
2. **The host logs must show the injected query actually did something** — executed, returned rows, or spawned a process — not an error, a syntax rejection, or a 403/deny.
3. **Packet metadata should show data leaving** or at least a substantive response, not a tiny error packet.
4. **Prior history on this asset** might change the reading (e.g. a corroborating exploit alert).

The severity_label "critical" is the sensor's opinion and I will not weight it.

**What would falsify success:** running version outside every affected range → `version_patched`; logs showing the injection errored out or returned zero rows → `logs_clean`; a tiny/benign flow with no outbound data → `packet_benign`.

Let me get the asset inventory and the CVE knowledge base in parallel — I need the running version and the affected ranges to do the join myself.

> **Version comparison, stated explicitly:**

- SRV-DB-02 runs **MySQL 5.7.21**.
- CVE-2023-21980 (`sql_injection`, CVSS 9.8) affects `>=5.7.0,<5.7.30`. **5.7.21 is inside that range** — it is above the 5.7.0 floor and below the 5.7.30 fix. This host **IS affected**.
- CVE-2022-21444 affects `>=8.0.0,<8.0.30`. The host runs 5.7.21, which is **outside** that range entirely — not applicable.

So `version_in_range` is established for a SQLi-class CVE whose description matches this signature's mechanism (crafted UNION payloads in the parser). The host is also a "Primary customer database" with critical criticality and a last patch date of 2024-02-11 — note the patch date is irrelevant to the version, since the running version is the fact that governs.

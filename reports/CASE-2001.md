### Sufficiency assessments

> **Initial hypothesis and test plan.**

The alert is a SQL Injection attempt (UNION SELECT) from 198.51.100.23 against SRV-DB-02 on port 3306 (MySQL). For this attack to have **succeeded**, all of the following would need to be true:
1. The MySQL build running on SRV-DB-02 must be inside the affected range of a relevant CVE (i.e., actually vulnerable), OR the injection must succeed via weak/absent auth regardless of CVE.
2. The host logs must show the injected query actually executing — rows returned, data read, a process spawned — not an auth error or syntax error.
3. Packet metadata must not show a simple "error/blocked" response; ideally it shows a payload anomaly or data leaving.

**Falsifiers I will look for:** a running version outside all affected ranges (patched), server logs showing the attempt erroring out / returning zero rows / being rejected, and packet metadata showing a tiny rejected exchange rather than data transfer.

Let me gather the host and CVE facts in parallel, since they are independent.

> This changes the picture decisively. Let me lay out what I now have:

**Version comparison (done explicitly):**
- SRV-DB-02 runs **mysql 5.7.21**.
- CVE-2023-21980 affects **>=5.7.0,<5.7.30** with attack_class **sql_injection**. **5.7.21 falls inside that range → this host IS affected.** And the description matches the alert exactly: "crafted UNION payloads… authentication bypass and arbitrary read of arbitrary tables by an unauthenticated remote attacker."
- CVE-2022-21444 affects >=8.0.0,<8.0.30 — 5.7.21 is outside that range and it's a DoS, not relevant here.

So the vulnerability side is established: unpatched, and the CVE's attack class matches the signature.

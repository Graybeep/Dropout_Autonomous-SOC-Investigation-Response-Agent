An alert is only a starting point, not a verdict

A detection signature fires when traffic looks like an attack. Whether the attack actually worked is a separate question, and answering it means going and checking. That is the whole job.

The six stages

The agent picks its own path through them

Nothing below is a fixed script. The agent decides which evidence to pull, in what order, and when it has enough to stop.

Alert

A detection alert opens a case: signature, source, destination, target asset, and the sensor's severity label.

Why it matters: the severity label is recorded as the sensor's opinion, never as a finding. A "critical" label earns no points in the score.

See it
ET WEB_SERVER SQL Injection Attempt UNION SELECT
198.51.100.23 to 10.20.2.22:3306 on SRV-DB-02, labelled critical by the sensor. At this point nothing is known except that traffic matched a pattern.

Hypothesis

The agent states what it believes happened, what evidence would confirm it, and what evidence would falsify it.

Why it matters: naming the disconfirming evidence up front is what stops the investigation becoming a hunt for agreement.

See it
Hypothesis: the injection succeeded and data was read.
Would confirm: a vulnerable version, logs showing the query executed, bulk egress.
Would falsify: a patched version, logs showing the request blocked or returning zero rows, or a control that made the read impossible.

Evidence

The agent chooses one tool call at a time, states its reason before making it, and judges after each result whether it has enough.

Why it matters: the order is the agent's, not ours. Two cases with the same signature routinely take different paths.

See it
Scenario 2 went get_alert, get_asset_info, get_packet_metadata, get_server_logs, get_related_alerts, get_vulnerabilities, get_configuration.
Each call carries the reason the agent gave before making it, and each result is followed by an explicit "do I have enough yet" judgement.

Verdict

The agent declares which classes of evidence it established and cites the tool result behind each. A fixed table turns those into a score and an outcome.

Why it matters: the agent never writes the confidence number. Ask where 0.95 came from and there is a one line answer, and the same evidence scores identically every run.

See it
Base 0.50, then version_in_range +0.25, logs_consistent +0.25, exfil_indicators +0.15.
Raw 1.15, clamped to 0.95, outcome SUCCEEDED. A submission citing a source that returned nothing is refused before it ever scores.

Action

A justified verdict blocks the source IP. An uncertain verdict on a critical asset contains precautionarily and says so. A failed attack gets no action at all.

Why it matters: containment under uncertainty is labelled as exactly that, so a precautionary block is never mistaken for a finding of breach.

See it
SUCCEEDED at 0.95 blocks. INCONCLUSIVE on a critical asset blocks with precautionary: true. INCONCLUSIVE elsewhere takes no action and flags for an analyst. FAILED does nothing.

Verification

The agent re-reads firewall state from disk and compares what it observes against what the policy expected.

Why it matters: requesting an action and achieving one are different events. The agent is not permitted to assume the block landed.

See it
After block_ip, the agent calls check_firewall_state, which reads the same file back from disk. Expected blocked true, observed blocked true. If those disagreed, the case would say so.
Evidence correlation

No single source answers the question

The vulnerability database is keyed by service name and holds no per-host patch status, because a real CVE feed does not know what your host runs. The agent has to join independent facts and show the join.

Asset
get_asset_info
SRV-DB-02 runs mysql 5.7.21
Vulnerability
get_vulnerabilities
CVE-2023-21980 affects >=5.7.0,<5.7.30
Configuration
get_configuration
the app account holds SELECT on every schema
↓
5.7.21 falls inside that range, and nothing in the configuration stops the read

Neither fact is a verdict on its own. The knowledge base never says "this host is vulnerable" and the host never says "this version is affected". That comparison is the agent's to make, and it appears in the trace as a step you can read.

The same join can point the other way. On SRV-HR-11 the version is in range and the injected query does reach the database, but the account it runs as holds no privilege on the targeted table, so the query returns zero rows. Same signature, opposite outcome, and only the configuration explains the difference.

Boundaries

What the agent can reach

Eleven tool schemas: eight that read evidence, two that act on the network, and one it submits its conclusion through. Everything sits inside a sandbox that is reset from a pristine copy before every run.

Read: evidence
  • get_alert
  • get_asset_info
  • get_vulnerabilities
  • get_configuration
  • get_server_logs
  • get_packet_metadata
  • get_related_alerts
  • check_firewall_state

Flat JSON files you can open and read yourself. A lookup that finds nothing returns an explicit "no data" rather than an empty answer.

Act: response
  • block_ip
  • unblock_ip

Both write to a sandboxed firewall state file, and check_firewall_state reads that same file back. The mutation is real inside the sandbox, which is what makes verification meaningful rather than decorative.

The eleventh schema, submit_assessment, is neither: it is how the agent declares what it found, and it can be refused.

Cannot access
  • Real hosts or production systems
  • Credentials of any kind
  • Live network traffic
  • Any outbound network call
  • The fixtures it was seeded from

Every hostname, IP, account and log line in this project is synthetic. No real system is described anywhere.

The trust moment

The agent does not assume its own action worked

This is the shortest section and the one that matters most. Requesting a block and achieving a block are two different events, and only one of them is evidence.

1. Verdict
SUCCEEDED at 0.95, above the action threshold
2. Action
block_ip writes the rule to firewall state
3. Re-read
check_firewall_state reads the file back from disk, not from memory
4. Confirm
Observed state compared against what the policy expected, and the result recorded either way

If the re-read disagreed with the expectation, the case would record the disagreement rather than the intention. A run where the block silently failed would show up as a failed check, not as a success.

Proof

It has to survive the cases that are not clean

Any system can look good on an obvious breach. These seven exist because the interesting failures are the ambiguous ones, and the outcomes are genuinely spread.

1
FAILED
a critical label on a patched host, correctly dismissed
4
SUCCEEDED
including one reopened by later evidence and one overturned by a human
2
INCONCLUSIVE
one capped by a failed tool, one by a gap we document rather than hide

The set deliberately includes a false alarm, a case where a tool fails mid-investigation, a case where an analyst overrules the agent and it must not re-block, and one case the scoring model cannot currently resolve. That last one is left failing on purpose.

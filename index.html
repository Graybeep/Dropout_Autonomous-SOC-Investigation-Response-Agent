How it works

Six stages, and the agent picks its own path through them

The alert arrives with no verdict attached. Everything below is the agent's own decision — which evidence to pull, in what order, and when it has enough to stop.

1

Ingest

An alert opens a case. Its severity label is recorded as the sensor's opinion, never as a finding.

2

Hypothesise

The agent states what would confirm the attack succeeded — and what would falsify it.

3

Gather

It chooses tool calls one at a time, giving a reason before each, and judges after each whether it has enough.

4

Score

It declares which classes of evidence it found, with citations. A fixed function turns those into a score.

5

Act

A justified verdict blocks the source IP in a sandboxed firewall file. An uncertain one on a critical asset contains precautionarily.

6

Verify

It re-reads firewall state from disk to confirm the block actually landed, rather than assuming it did.

The correlation that matters

The vulnerability database is keyed by service name and holds no per-host patch status — a real CVE feed does not know what your host runs. So the agent has to join two independent facts and show its working:

get_asset_info → the host runs MySQL 5.7.21
get_vulnerabilities → CVE-2023-21980 affects >=5.7.0,<5.7.30
→ 5.7.21 is inside that range → vulnerable

The configuration source follows the same rule. It describes controls — which tables an account may read, whether the web firewall blocks or merely logs — and never says whether they stopped this attack. That judgement stays the agent's, and it is visible in the trace.

Seven scenarios

Each one is a different way to be wrong

Every scenario runs the same loop over different evidence. The outcome is what the scoring function produced — SUCCEEDED means the attack worked, so it is the bad news, and FAILED is the good news.

1

False alarm, patched host

A critical-labelled injection alert against a host running a version outside every affected range, whose logs show the request was blocked before it reached the database.

FAILED — attack did not work
2

True positive, unpatched host

The same signature, a vulnerable version, and logs showing the query ran and data left the host. The source IP is blocked, then the block is verified from disk.

SUCCEEDED — attack worked
3

Delayed evidence

Ambiguous at first. New evidence arrives naming a second host, so the agent forms a fresh hypothesis and goes and investigates that host rather than just re-scoring.

SUCCEEDED — after re-opening
4

Human override

An analyst overrules the verdict. The agent unblocks, records the override beside its own prior conclusion, and does not re-block on its own.

SUCCEEDED — then overridden
5

Multi-alert correlation

A second alert on the same asset opens its own case, discovers the first, and both conclusions move on the strength of the other.

SUCCEEDED — two cases
6

Tool failure

The log source fails. The agent notices, retries, routes to another source, and refuses to treat missing evidence as evidence that nothing happened.

INCONCLUSIVE — capped on purpose
7

Configuration prevents it

Vulnerable version, attack visible in the logs — but the database account cannot read the targeted table. The agent establishes this and says so; the scoring model has no term for it, so the case is left short of a verdict.

INCONCLUSIVE — declared limitation
Why it is built this way

The score is arithmetic. The reasoning is the agent's.

The agent never emits a confidence number. It declares which classes of evidence it established and cites the tool result behind each one; a fixed table turns those into a score. Ask where 0.95 came from and there is a one-line answer, and the same evidence scores the same way every time.

Submissions pass through a checker that can refuse them. It never decides whether a version falls in a range — that is the agent's call. It refuses the form of a claim: saying a host is outside all affected ranges having looked up only some of its services, or citing a source that came back empty.

Refusal is routine rather than exceptional, and both the refusal and the correction stay in the trace. Scenario 1 is the clearest case — the agent is refused on two counts at once, then resolves each differently: it fetches the data it was missing, and drops the claim it could not support.

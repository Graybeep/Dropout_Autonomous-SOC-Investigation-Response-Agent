Seven scenarios

Each one is a different way to be wrong. Every scenario runs the same loop over different evidence, and the outcome shown is what the scoring function produced. SUCCEEDED means the attack worked, so it is the bad news, and FAILED is the good news.

1

False alarm, patched host

A critical-labelled injection alert against a host running a version outside every affected range, whose logs show the request was blocked before it reached the database.

FAILED: attack did not work
2

True positive, unpatched host

The same signature, a vulnerable version, and logs showing the query ran and data left the host. The source IP is blocked, then the block is verified from disk.

SUCCEEDED: attack worked
3

Delayed evidence

Ambiguous at first. New evidence arrives naming a second host, so the agent forms a fresh hypothesis and goes and investigates that host rather than just re-scoring.

SUCCEEDED: after re-opening
4

Human override

An analyst overrules the verdict. The agent unblocks, records the override beside its own prior conclusion, and does not re-block on its own.

SUCCEEDED: then overridden
5

Multi-alert correlation

A second alert on the same asset opens its own case, discovers the first, and both conclusions move on the strength of the other.

SUCCEEDED: two cases
6

Tool failure

The log source fails. The agent notices, retries, routes to another source, and refuses to treat missing evidence as evidence that nothing happened.

INCONCLUSIVE: capped on purpose
7

Configuration prevents it

Vulnerable version, attack visible in the logs, but the database account cannot read the targeted table. The agent establishes this and says so; the scoring model has no term for it, so the case is left short of a verdict.

INCONCLUSIVE: declared limitation
